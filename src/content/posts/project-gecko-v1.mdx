## What's this about

I tried to create a basic type checker in Python ([here](/posts/type-checker-python)), and realised how hard it was. 
But because the topic really interested me, I decided to scope out a proper basic structure for an MVP tool which 
could type check python and cover the gaps (mainly type provenance) of modern tools like MyPy/Pyright etc...

Repo: [github.com/JeremyQuek/gecko](https://github.com/JeremyQuek/gecko)

## Project Architecture

Right! So a type analyzer roughly needs 3 layers of logic to execute properly:

1) Module Analyzer: Called by Project Manager to extract types on a single file [Completed]
2) Project Analyzer: Inspects the entire project, the interpreter env, and creates a dependency graph amongst files [In Progress]
3) Core Engine: Delegates the task to the Project Analyzer and interfaces with the LSP

## Single File Analysis

<img src={geckoModulesImg.src} alt="UML Module Diagram" width="700" />
<div align="center">Module Dependency and API Graph</div>

The analysis of a program requires many steps. I used Python's in-built `ast` module to generate an AST.

The main controller, `ModuleAnalyzer`, oversees the generation of the control flow graph using
the `ASTWalker` class. 

It owns the graph traversal logic using a topological sorting order. It calls `CodeBlockAnalyzer` on each graph node (a chunk
of program text) to process and persist type information into a symbol table.

### Store and LEGB

A `LexicalEnvironment` object stores a stack of symbol tables.
The stack naturally models Python's [LEGB semantics](https://realpython.com/python-scope-legb-rule/). 

<img src={LEGBImg.src} alt="LEGB Diagram" width="700" />

A stack naturally captures this lookup behaviour.
Let's say we're trying to process `x : int = 5`, and want to know which `x` we're referring to, we would:

1) Lookup the `local` scope, which is the topmost symbol table in the stack
2) Lookup `enclosures`, which would be the middle symbol tables
3) Refer to the `global` table, which is the lowest table on the stack

And finally the built-in which is a standard for all Python programs.

As we move into and out of procedure calls, the stack pops and pushes a frame and naturally models the environment.

### Environment Capturing

Storing a `LexicalEnvironment` as the symbol object store, and a 1:1 mapping to a graph node gives us nice properties like
being able to model branching naturally as the environment is 'cloned' for the two child branches.

<img src={environmentCloneImg.src} alt="Clone Diagram" width="700" />
<div align="center">Environment Cloning on Branching </div>

It allows us to easily capture a [closure environment](https://realpython.com/python-closure/) for a function,
by noting the instance of `LexicalEnvironment` at the entrypoint of a function definition subgraph.

### Writing to an Output

The output is streamed to an output data structure. Ideally this is done asynchronously, so that the upstream engine and project level
controllers can showcase the type information as soon as they're ready.

*But what if a symbol's type information is not complete when first published?*

Because the graph analysis is done topologically, this ensures that all sections of a program that have a bearing on the type of a
variable `x` (the "flow" of the program into `x`) must be processed before `x` can be.

This ensures that when we process a node, we always have all prerequisite knowledge required to analyze it.
