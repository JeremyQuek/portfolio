## What is a shell?

I've always conveniently thought of shells as magical black boxes, but what they actually do is built from really intuitive Unix building blocks.

<img src={shellArchImg.src} alt="Shell architecture" width="700" />

A shell is a program that spins on user input. That input usually points to either a shell builtin command, or to an executable file. There's also shell languages but we'll get into that later. Basically shells are control panel programs that let you run other programs. When I spin up a shell and type `ls`, the parent shell forks a child process called `ls` and runs it with the arguments I provide. That's it!

---

## File descriptors: how output works

So how does the shell actually redirect output? When any process opens up, it always has 3 basic file descriptors: stdout (fd 1), stdin (fd 0), and stderr (fd 2).

What are file descriptors? They're just integers. They point towards the process's file descriptor table, which in turn points to the actual file struct in the operating system (differs for different OSes). This is part of the Unix [*Everything is a file*](https://en.wikipedia.org/wiki/Everything_is_a_file) philosophy.

<img src={fdImg.src} alt="File descriptor table" width="700" /> 

When the parent shell forks a child process, the child inherits the parent's descriptors. The parent then executes a `wait()` on the child, while the child's output is redirected to the parent's PTY.

This is why when you run a compiled C exectuable, or a program like `brew` in your terminal, the output from that process initiated from the shell gets sent to the same terminal device as the shell.

This is the foundation for everything else in the shell.

## The first surprise: cd isn't a program

One thing that surprised me early on was that `cd` isn't actually an executable sitting somewhere in `/usr/bin`. I spent a while wondering why, until it clicked: changing directories affects the *current* process. If my shell forked a child to run `cd`, only the child would move into the new directory before immediately exiting. My shell would still be sitting in the original location. That's why `cd` has to be a builtin, calling `chdir()` directly in the shell process itself.

`pwd` is similar. Just calls `getcwd()` and prints it. But having to think about *why* these are builtins rather than programs was the first moment where process isolation became real to me.

---

## fork() returns twice

The first time I called `fork()`, it felt almost magical. The function returns *twice*. Once in the parent, once in the child. Suddenly there are two copies of my shell running. The only difference is the return value.

In the parent, `fork()` returns the child's PID. In the child, it returns 0. That's how I know which one I am. Then the child calls `execv()` to replace itself with whatever program you actually wanted to run, and the parent calls `wait()` to block until it's done.

Conceptually simple. But I spent way too long debugging why arguments weren't being passed correctly. `execv` wants a null-terminated array of strings, and I kept forgetting the null terminator. Classic off-by-one energy.

---

## Path resolution: why I had to type /usr/bin/wc

Initially I had to type full paths like `/usr/bin/wc` to run anything. So annoying. The fix is PATH resolution: I grab the `PATH` environment variable, split it by `:`, and for each directory check if the program exists there. First match wins.

I couldn't use `execvp` (assignment rules said no), so I implemented my own resolution with `execv`. Honestly this was good because now I actually *understand* what PATH does rather than just knowing it exists. It's literally just a list of directories to search through. That's it. No magic.

## Everything is file descriptors

This was the realization that tied everything together. Before this project, redirection, pipes, and stdout all felt like separate concepts. They're not. They're all the same thing: file descriptors.

```
echo hello           → stdout (fd 1) → terminal
echo hello > out.txt → stdout (fd 1) → file  
echo hello | wc      → stdout (fd 1) → pipe
```

Nothing inside `echo` changes in any of these cases. It always just writes to fd 1. The shell changes *what fd 1 points to* before calling exec. That's redirection. That's pipes. That's everything.

I expected redirection to require changing every program I executed. Turns out it requires changing none of them. I just replace file descriptor 1 with a file using `dup2()`, call `exec()`, and the program happily writes into the file without realizing anything changed.

## Pipes: the part that broke me

I always thought `|` was some magical shell syntax. It isn't. A pipe is literally just a tiny kernel buffer with two file descriptors attached to it.

```
grep foo
    stdout
      │
      ▼
┌─────────────┐
│ kernel pipe │
└─────────────┘
      │
      ▼
  sort
   stdin
```

The `pipe()` syscall gives two fds: a read end and a write end. I use `dup2()` to wire process A's stdout into the write end, and process B's stdin into the read end. Done.

Except not done at all. Because if I forget to close *any* unused pipe fd in *any* process, everything hangs. No error. No crash. Just silence.

Why? If the reader still has an open write-end fd, it'll wait forever for data that'll never come. If the writer still has an open read-end fd, it doesn't know nobody's reading anymore.

I had to support arbitrary chains (`A | B | C | D`), which means n-1 pipes for n processes. Getting the fd cleanup right across all of them took me a full evening. The hanging bugs were the worst because there's literally no feedback. Your shell just... stops.

## Signals: don't kill the shell

When you press Ctrl+C, your terminal sends SIGINT to the foreground process group. Problem: if your shell is in the foreground group, Ctrl+C kills the shell too.

The fix is process groups. I put each child process in its own group using `setpgid()`, and use `tcsetpgrp()` to make the child's group the foreground while it's running. When the child finishes, I give the foreground back to the shell.

This way Ctrl+C only kills the running program. Same deal with Ctrl+Z for pausing.

---

## Background processes and zombies

Adding `&` at the end runs a command in the background. The shell just doesn't call `wait()` immediately.

But here's the thing nobody warns you about: zombie processes. When a background process finishes, it doesn't fully disappear. It sits there as a zombie until the parent calls `wait()`. If you never reap them, they accumulate.

I added a non-blocking `waitpid` check with `WNOHANG` before each prompt to clean these up. Felt hacky, but that's genuinely how real shells handle it.

---

## Parsing: the part nobody talks about

Most people know fork and exec exist. But fewer think about how a shell turns this:

```
cat input.txt | grep foo > out.txt &
```

into something executable. I need to figure out:
- There are two commands separated by `|`
- The second command redirects stdout to `out.txt`
- The whole thing runs in the background

I built a simple tokenizer that splits on spaces, then walks through looking for special characters (`|`, `<`, `>`, `&`). Each command becomes a struct with its argv, input source, output destination, and whether it's backgrounded.

## Connecting to a PTY

So what's a TTY? It stands for "teletypewriter", a relic from when terminals were literally physical typewriters connected to computers over serial lines. These days a TTY is just the kernel abstraction that handles your terminal I/O: it buffers input, handles line editing, processes special characters like Ctrl+C, and connects your shell's stdin/stdout to the screen.

When I open Terminal.app, the system creates a PTY and hooks my shell up to it. The shell reads from the my keyboard input and writes to the text on screen.

### Using Electron to simulate a PTY 

Instead of properly wiring up a PTY, I piped the shell's stdout into an Electron application (sounds absurd but I just wanted something *cool*). That's what gave the shell that matrix-y look in the screenshot at the top of this blog!

Building a terminal wasn't really part of the project though, so I mostly vibe-coded the frontend portions and only did the wiring myself.  I wrote a bash script that launches the Electron app, the Electron app then forks my shell process and connects to it via fd sharing, spinning in a loop reading its output and rendering it into the custom UI.

## What clicked

Before this project, `fork`, `exec`, `dup2`, and `pipe` felt like unrelated POSIX APIs I'd memorized for exams. Building a shell made me realize they're really just a handful of composable primitives. Once you understand processes and file descriptors, features like redirection, pipelines, and background jobs almost fall out naturally.

The Unix philosophy isn't just "do one thing well." It's "make everything a file descriptor and let people compose them." Building a shell is probably the fastest way to internalize that.
