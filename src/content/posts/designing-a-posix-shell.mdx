## What is a shell?

I've always conveniently thought of shells as magical black boxes, but what they actually do is built from really intuitive Unix building blocks.

<img src={shellArchImg.src} alt="Shell architecture" width="700" />

A shell is a program that spins on user input. That input usually points to either a shell builtin command, or to an executable file. There's also shell languages but we'll get into that later. Basically shells are control panel programs that let you run other programs. When I spin up a shell and type `ls`, the parent shell forks a child process called `ls` and runs it with the arguments I provide. That's it!

---

## File descriptors: how output works

So how does the shell actually redirect output? When any process opens up, it always has 3 basic file descriptors: stdout (fd 1), stdin (fd 0), and stderr (fd 2).

What are file descriptors? They're just integers. They point towards the process's file descriptor table, which in turn points to the actual file struct in the operating system (differs for different OSes). This is part of the Unix [*Everything is a file*](https://en.wikipedia.org/wiki/Everything_is_a_file) philosophy.

<img src={fdImg.src} alt="File descriptor table" width="700" /> 

When the parent shell forks a child process, the child inherits the parent's descriptors. The parent then executes a `wait()` on the child, while the child's output is redirected to the parent's PTY.

This is why when you run a compiled C exectuable, or a program like `brew` in your terminal, the output from that process initiated from the shell gets sent to the same terminal device as the shell.

This is the foundation for everything else in the shell.

## Builtins: cd isn't a program

One thing that surprised me early on was that `cd` isn't actually an executable sitting somewhere in `/usr/bin`. 
There are number of such shell commands which are builtins - commands implemented directly within the shell.

If you're on zsh/bash, you can run `which $cmd` to see the executable binding of that command in your shell!
Doing it for pwd/cd will likely show:

```

user(laptop) ~/ % which pwd
pwd: shell built-in command
user(laptop) ~/ % which cd
pwd: shell built-in command

```

Changing directories affects the *current* process. 
If my shell forked a child to run `cd`, only the child would move into the new directory before immediately exiting. 
My shell would still be sitting in the original location. That's why `cd` has to be a builtin, calling `chdir()` directly in the shell process itself.

`pwd` is similar. Just calls `getcwd()` and prints it. But having to think about *why* these are builtins rather than programs was the first moment where process isolation became real to me.

## fork() returns twice

`fork()` is a pretty basic Unix convention. It allows you to create a process thats a clone of the parent.

> There's an interesting piece of [history](https://www.microsoft.com/en-us/research/publication/a-fork-in-the-road/) as to why `fork()` is designed this way instead of starting up a fresh "empty process"

The interesting thing about `fork()` is that because the child proc is clone, at the instance `fork()` completes both parent and child are executing on the
same line of code!

```c

pid_t pid = fork(); // <- This is where the instruction pointer returns to in both child and parent!

if (pid == 0) {
    // child process
    execv("/bin/ls", args);
} else {
    // parent process
    waitpid(pid, &status, 0);
}

```

For the parent `fork()` returns the child pid, while the it returns 0 for the child. 
You can imagine that the kernel internally restores the execution context for the child and parent with different values in the `EAX/RAX`!
 
From here, the child typically calls `execv()` to replace itself with whatever program you actually wanted to run, and the parent calls `wait()` to block until it's done.

This is the foundation of Unix process creation and there are other interesting nuances like [Copy-on-write](https://en.wikipedia.org/wiki/Copy-on-write)!

## Path resolution

So to actually run child executables like `grep`/ `ls`, the shell has to be able to find where the binary lives.
Most shell softwares like zsh come with preconfiguerd paths and good heuristic lookup hierachies to find them.

This is highly OS dependent, so instead of creating my own path hierachy, I just borrowed the `$PATH` variable from the
parent shell that runs my shell.

You can run `echo $PATH` on your zsh/bash shell and it will show something like this:

```bash

$echo$PATH
/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin

```

> For obvious purposes this is not the actual a snippet of my shell's `$PATH`

Shell's also supporting caching paths for quick lookup, you can run `hash` on your shell and see the internal hash table

```
$ hash
hits	command
   12	/usr/bin/ls
    5	/usr/bin/cat
    3	/usr/bin/git
    8	/usr/bin/python3
    2	/usr/bin/vim
    6	/usr/bin/ssh
    1	/usr/bin/make
    4	/usr/bin/docker
    7	/bin/grep
    9	/bin/sed
```

I also implemented a hash table that would cache commands to their paths when executed once before so that the shell doesnt have to search again.
As a bonus I also configured it so that on launch, my shell inherits the parent's hash table and `$PATH`!

## Everything is file descriptors

Now I can find and run child processes, but I couldn't see their output yet.

Most of shell's output and input manipulation is fd redirection. As mentioned fds are just integer indexes into ure process file table, which itself is also just a pointer table.


### Stdin and Stdout

Stdin, stout is what process typicall write/read to using `printf()/print()` and `input()/cin` (and other canonical language methods).
When you run a python script, or executable or a git command, their outputs are written to stdout which is terminal you executed them from.

> Did you know that in C, `printf()` is also an internally buffered user space library around the system call write() to stdout?

FDs can also be manually changed using `dup()`, `dup2()` from the [`<unistd.h>`](https://pubs.opengroup.org/onlinepubs/9699919799/basedefs/unistd.h.html) library!

```
echo hello           → stdout (fd 1) → terminal
echo hello > out.txt → stdout (fd 1) → file  
echo hello | wc      → stdout (fd 1) → pipe
```

Nothing inside `echo` changes in any of these cases. It always just writes to fd 1. The shell changes *what fd 1 points to* before calling exec. 

I expected redirection to require changing every program I executed. Turns out it requires changing none of them. I just replace file descriptor 1 with a file using `dup2()`, call `exec()`, and the program happily writes into the file without realizing anything changed.

## Pipes: the part that broke me

I always thought `|` was some magical shell syntax. It actually creates a [pipe](https://en.wikipedia.org/wiki/Pipeline_(Unix)) between two separate processes. A pipe is just a kernel buffer with two file descriptors attached to it.

<img src={pipeImg.src} alt="Pipe diagram" width="700" />
<div align="center">A Unix Pipe Under The Hood</div>

The `pipe()` syscall gives two fds: a read end and a write end. I use `dup2()` to wire process A's stdout into the write end, and process B's stdin into the read end.

### File Descriptor leaks

If I forget to close *any* unused pipe fd in *any* process, it leads to silent fd leaks, so its important to be explicit in manual FD manipulation here.

If the reader still has an open write-end fd, it'll wait forever for data that'll never come. If the writer still has an open read-end fd, it doesn't know nobody's reading anymore.

I had to support arbitrary chains (`A | B | C | D`), which means n-1 pipes for n processes. Getting the fd cleanup right across all of them took me a full evening. The hanging bugs were the worst because there's literally no feedback. Your shell just... stops.

## Signals: don't kill the shell

If you're a dev, you would definintely have hit Ctrl+C on your shell before. This is known as a [signal](https://en.wikipedia.org/wiki/Signal_(IPC)).

### What are Signals
Signals are a process control mechanism implemented at the kernel level. Each time before your scheduled process is run, the kernel does a quick check on the `pending_signals` 
mailbox (inside the PCB) and switches execution based on the type of signal received. This is done via bitwise math and direct Instruction pointer manipulation so its very fast

This is the reason why you can Ctrl+C a hanged shell process and it 'responds'


### Process groups

A process group is a logical construct that lives as an int inside the PCB.

Say you spin up something like a pipe chain:

```
cat file | grep "x" | wc -l
```

If you Ctrl+C this shell, which process are you talking to? You should be targeting all of them right?

Or if your run a process, which itself creates other child process, the Ctrl+C signal should not just reach the shell's child but all its grandchildren as well (Or your would have orphans)! 

Or what if your shell is in the foreground group, Ctrl+C kills the shell too!

The fix is have separate process groups. I put each child process in its own group using `setpgid()`, and use `tcsetpgrp()` to make the child's group the foreground while it's running. When the child finishes, I give the foreground back to the shell.

This way Ctrl+C only kills the running program.

## Background processes and zombies

Adding `&` at the end runs a command in the background. The shell just doesn't call `wait()` immediately.

But here's the thing nobody warns you about: zombie processes. When a background process finishes, it doesn't fully disappear. It sits there as a zombie until the parent calls `wait()`. If you never reap them, they accumulate.

I added a non-blocking `waitpid` check with `WNOHANG` before each prompt to clean these up. Felt hacky, but thats generally how some shells handle it.

## Parsing: the part nobody talks about

Finall, while I had already implemented each individual mechanism, I still need to handle chained commands like this: 

```
cat input.txt | grep foo > out.txt &
```

Turning this into something executable need tokenizing and parsing, almost like a mini language! I need to figure out:
- There are two commands separated by `|`
- The second command redirects stdout to `out.txt`
- The whole thing runs in the background

> Real shells have [shell language interpreters](https://www.gnu.org/software/bash/manual/bash.html#Shell-Syntax), implementing full ASTs 

I built a simple tokenizer that splits on spaces, then walks through looking for special characters (`|`, `<`, `>`, `&`). Each command becomes a struct with its argv, input source, output destination, and whether it's backgrounded.
Although in theory shells should support a full shell language file, that would be too complex for now...

### Using Electron to simulate a PTY 

Instead of wiring up a real PTY, I piped the shell's stdout into an Electron application (sounds absurd but I just wanted something that looks *fancy*). That's what gave my terminal that matrix-y look in the screenshot at the top of this blog!

Building a terminal wasn't really part of the project though, so I mostly vibe-coded the frontend portions and only did the wiring myself.  I wrote a bash script that launches the Electron app, the Electron app then forks my shell process and connects to it via fd sharing, spinning in a loop reading its output and rendering it into the custom UI.

## What clicked

Before this project, `fork`, `exec`, `dup2`, and `pipe` felt like unrelated POSIX APIs I'd memorized for exams. Building a shell made me realize they're really just a handful of composable primitives. Once you understand processes and file descriptors, features like redirection, pipelines, and background jobs almost fall out naturally.

The Unix philosophy isn't just "do one thing well." It's "make everything a file descriptor and let people compose them." Building a shell is probably the fastest way to internalize that.
