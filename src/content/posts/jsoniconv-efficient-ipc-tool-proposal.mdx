## What's this about

 During my time at Stripe, I encountered this internal IPC tool called JsonIconv. And I was genuinely baffled by how inefficient it was.

---

## What is IPC?

Inter-process communication is the means by which two processes talk to each other, typically on the same machine. 
There are a many ways to do it: shared memory, Unix sockets, pipes, message queues, gRPC, REST, carrier pigeons

The key question is always: how do I serialize the data so both sides understand it?

### Where Iconv comes in 

Iconv is a program used to convert between different character encodings. This is useful if one application receives say
ISO-8859-1 encoding and the other expects UTF-8 encoding


---

## Enter JsonIconv

Hmm...okay so it seems that somebody thought that it would be good idea to implement Iconv tool in Java with JSON as the intermediate serialisation.

JSON is a text format. It's human readable. But it's also rather wasteful serialisation where they are leaner options available.
An integer like `1000000` takes 7 bytes as a string. As a 32-bit int? 4 bytes. As a varint? Maybe 3.
A systems person would probably feel the mild discomfort here.

```
Your data (small)
    │
    ▼
Serialize to JSON (bigger)
    │
    ▼
Add framing headers (even bigger)
    │
    ▼
Encode the whole thing as UTF-8 bytes (somehow bigger still)
    │
    ▼
Send over the wire
    │
    ▼
Reverse all of the above on the other side
```

Safe to say, this tool gets a notorious reputation for obvious reasons...

## How I would make it better

Instead of using json and pipes which are far too efficient, I thought we should go with a more intuitive approach

A potential IPC technique could have the sender process spins up a virtual screen device and *renders* the bytes as pixels on screen. The recipient process would then spin up an OCR model and *infers* the bytes from the image.

This approach would be a high risk, no rewared approach in low accuracy and high latency, esp given that OCR models today are basically *always* determinstic. The benefit of spinning up a virtual screen means that we could use screenshots as paper trails and maybe autonomate screnshotting the device with Hammerspoon, and export the data to CDC.

Overall, I think this would be a much cleaner architecture than JSON.
