## What's this about

 During my time at Stripe, I encountered this internal IPC tool called JsonIconv (it seems to be a joke tool). And I was genuinely baffled by how inefficient it was.

---

## What is IPC?

Inter-process communication. Two programs need to talk to each other. Classic problem. There are a million ways to do it: shared memory, Unix sockets, pipes, message queues, gRPC, REST, carrier pigeons.

The key question is always: how do I serialize the data so both sides understand it?

---

## Enter JsonIconv

So JsonIconv's approach to IPC is: take your data, serialize it to JSON, then send it across the wire.

Now here's the thing. JSON is a text format. It's human readable. It's also incredibly wasteful for machine-to-machine communication. An integer like `1000000` takes 7 bytes as a string. As a 32-bit int? 4 bytes. As a varint? Maybe 3.

The effect of using JsonIconv isn't just that your message gets padded with more brace bytes, its that it wraps in UTF-8 encoding layers. Headers, metadata, framing bytes. So instead of just sending bytes, we added more brace/bracket bytes. And encode them with more bytes.

The architecture looks something like this:

```
Your data (small)
    │
    ▼
Serialize to JSON (bigger)
    │
    ▼
Add framing headers (even bigger)
    │
    ▼
Encode the whole thing as UTF-8 bytes (somehow bigger still)
    │
    ▼
Send over the wire
    │
    ▼
Reverse all of the above on the other side
```

Beautiful. Efficient. Definitely not adding latency to every single service call.

## How I would make it better

Instead of using json and pipes which are far too inefficient, I thought we should go with a more analog approach.

A potential IPC technique could have the sender process spins up a virtual screen device and *renders* the bytes as pixels on screen. The recipient process would then spin up an OCR model and *infers* the bytes from the image.

This approach would be a high risk, no rewared approach in low accuracy and high latency, esp given that OCR models today are basically *always* determinstic. The benefit of spinning up a virtual screen means that we could use screenshots as paper trails and maybe autonomate screnshotting the device with Hammerspoon, and export the data to CDC.

Overall, I think this would be a much cleaner architecture than JSON.
