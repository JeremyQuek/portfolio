## How does type checking even work?

Type checkers analyze your program without running it. To do that, we need to first represent Python as structured data.
There is where an Abstract Syntax Tree (AST) comes in. ASTs are tree representations of programming languages.

<img src={astImg.src} alt="Abstract Syntax Tree" width="700" />
<div align="center">Example of an AST</div>

### A Simple Analogy

Okay, if you're like me, I had no clue what I was looking at when I saw it for the first time.
But, one analogy which helped was thinking of a AST an a representation of grammatical structure. Say you have an sentence: "The cat sat on the mat".

You have the sentence

You have the subject "Cat"

You have the verb "sat"

You have the destination "mat"

The english language can be represented as a grammar tree!

Like diagramming a sentence. "The cat sat on the mat" becomes a tree with "sat" as root, "cat" as subject, "mat" as location. Same thing but for code. 
Did you know that all programming languages are grammar composed languages? Look it up! It's called [*Context Free Grammar*](https://en.wikipedia.org/wiki/Context-free_grammar)

### How do we create and use ASTs

Typically ASTs are created using lexers (DFA/NFA) to tokenize the program file, and then parser to turn it into a tree (recursive or stack based). 

An AST is incredibly useful because it gives us a structured representation.

<div align="center">A simple exercise</div>
```
for i in range(x):
  x = 1+2
```

Lets try turning the above snipper into an AST!
We see a for loop, so we know that we need a for node.

Then we have the body expression, which is a assignment statement.
On the left we have the target symbol x, and on the right the expression, which has two ints and an operator

## Data flow analysis and control flow graphs

So what are these things? I kept seeing these terms around and got annoyed of not knowing them, but turns out their really intuitive!


After we create a program tree, we might want to take tree and use it create a *control flow graph*. While an AST tells us what the program is,
the control flow graph tells us how the program runs.

*Lets visualise why we might need a graph*

<img src={dataFlowImg.src} alt="Data flow analysis" width="700" />


As we saw, depending on the branch that executes, `y` has either value 2 or 3. 
We also need to *remember* what the type was before and after the branch, this is where we need to *flow* the data through the graph like we're actually running the program!
This is what helps us answer the question, what is the type of symbol x at this part of the program!

### Cool fact
Woah, so do most compilers and type systems maintain some sort of internal graph? Yes they do! It's what is primary used for optimizations and typing statically. 
However, I thought that I could do away with the CFG for now and simply recurse on the AST. Well we'll see how well that goes...


### What I did

While a graph was ideal, and I eventually did sit down to properly design one, on my first iteration I decided to skip it
and just recurse on the AST; I wrote a script that basically walks down the tree from `ast` module, and memorises the type for each symbol at each node.

## What Do We To Store Type Information? 

When traversing the graph, what actual data structure should I use to store the type information?

Think about it - I needed to persist a key-value pair of symbol-to-type. What does this point to naturally?
A hash table! Or more accurately a **stack** of hash tables. 

<img src={symbolTableImg.src} alt="Data flow analysis" width="700" />

As we move through functions for instance, there could be two `x` active at once, a local `x`
and a global `x`. This means that its not enough to have one table, we need a hierachy of tables that mimic a lexical environment!


### What I did

As I was traversing down my AST, I maintain a stack of tables, which I pushed and pop each time I entered and exited a frame or changed scope (e.g entering a class body)

## MyPy already exists though

This is where I felt dumb. MyPy, Pyright, Pyre... years of engineering already done. But after a bunch of research I noticed none of them solved what actually bugged me: type *provenance*.

I don't just want to know a function returns `Dict[str, Any]`. I want to know *where* that type came from. Base class three levels deep? Metaclass? Decorator that mutated the return type?
