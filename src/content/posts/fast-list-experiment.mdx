## What this is about

If you've ever looked into how stock exchanges actually work under the hood, you'll find this thing called an order book. It's basically a giant list of buy and sell orders waiting to be matched. Every time someone wants to buy 100 shares of AAPL at $150, that order sits in the book until someone else is willing to sell at that price.

Now here's where it gets interesting. High frequency trading firms care about this structure *a lot*. We're talking about firms that spend millions on shaving microseconds off their execution time. They co-locate servers next to exchanges, use custom network cards, even care about the length of their fiber optic cables. And at the core of all that infrastructure? The order book. It needs to support insanely fast insertions (new orders flooding in), removals (cancellations, which happen way more often than you'd think), and lookups (matching engines finding the best price).

The data structures these firms use are optimized down to the cache line level. I always found that fascinating, so I wanted to see if I could build something inspired by those principles

## What I built

I wanted to create a basic version of a container in C++ that supports super fast operations for adding and removal, borrowing the concepts used in real HFT order books. The goal was simple: make a list that's as fast as physically possible on modern hardware.

What I ended up with is a memory contiguous doubly linked list. Sounds contradictory right? Linked lists are supposed to be scattered all over memory. But that's exactly the trick. I preallocate a fat contiguous buffer and manage the linking within it. You get the O(1) insertion/deletion semantics of a linked list with the cache performance of an array.

I found that this list supports an average of up to **41 million ops/s**, including FIFO ops + random access/removal.

The randomized mixed operations test (first test) is probably the most realistic one. I discovered the slowdown there is likely due to a collapse in branch prediction support, simulating real hot path conditions. In a real order book, you'd have a mix of adds, cancels, and matches all interleaved, so this test is the one I care about most.

One thing I found cool is that **fast list supports both random access and removal** while `std::list` doesn't even have that. In `std::list`, if you want to remove a specific order by ID, you need to walk the entire list O(n) to find it. In a real trading system, cancellations are the most common operation (some estimates say 90%+ of orders get cancelled), so this matters a lot.

## How I designed the list

I made the list structs 16 bytes each, which turned out to be super cache friendly. I used an array map with indices as IDs to prevent hash overhead:

- The *i*th index of the array = *i*th memory slot

**What it supports:**
- Add to back O(1)
- Remove from front & back O(1)
- Access and remove at random O(1)

In theory it could also support adding to front O(1) and adding to random O(1). I didn't implement those because for an order book you almost always just append to the back (new orders go to the end of the price level queue).

## Key optimizations I used

1) **Memory contiguity.** I preallocated enough buffer for up to 1 million nodes contiguously, leveraging cache locality in CPU access. This is the big one. Modern CPUs are insanely fast at sequential memory access but terrible at pointer chasing. A regular `std::list` allocates each node separately on the heap, scattering them all over memory. My approach keeps everything together.

2) **Cache friendliness.** I designed the list node structs to be 16 bytes, so each cache line (64 bytes) fetches 4 structs at once. This means when you're iterating through the list, you're almost never waiting on memory.

3) **Memory alignment.** I used aligned alloc to ensure the buffer is 64 byte aligned, perfect for cache fetch. Without this, your buffer might straddle cache line boundaries and you'd waste fetches.

4) **Prefaulted pages.** Pages are prefaulted upon allocation. I found this ensures even faster access time since we can leverage TLB. Without prefaulting, the first access to each page triggers a page fault, which is expensive.

5) **Doubly linked list.** Allows O(1) insertion and delete from both ends. The "doubly" part is key because it lets you remove a node without needing to find its predecessor first.

6) **Node ID array.** Uses an array of booleans where each index points to an *i*th slot using only pointer math, no hashing needed. This is how we get O(1) random access. Given an order ID, you just index directly into the array. No hash function, no collision handling, no overhead.

7) **Free list.** I dynamically append removed nodes to a free vector, allowing memory reuse while keeping FIFO order intact. When a node gets removed, its slot goes back into the free pool. Next insertion grabs from the free pool first before extending into fresh memory.

## What I took away from this

Building this taught me that the gap between "theoretically O(1)" and "actually fast" is enormous. `std::list` is O(1) insertion/deletion too, but it's 7-11x slower in practice because of cache misses. The algorithmic complexity is the same, but the constant factor is dominated by memory access patterns.

It also gave me a new appreciation for what HFT firms are doing. My little experiment hits 41M mixed ops/s on a laptop. Real production order books at firms like Citadel or Jump Trading are doing this at even lower latencies on custom hardware with kernel bypass networking. The rabbit hole goes deep.
